## 1. 项目采用什么许可

延续仓库现有根 [LICENSE](<../LICENSE>)：项目维护的源代码采用 **MPL-2.0**，package.json 和 lockfile 同步标注。已有第三方文件的原许可证、版权声明和例外优先；vendor、reference、SDK运行库、图片/示例等不因处于此仓库而被重新许可。

- MPL 是文件级的源码义务，不能把含有 MPL 代码的适配文件简单改标 MIT 或闭源并去掉原声明。
- 根 MPL 不要求把整个较大作品的所有独立文件一律改成 MPL；本项目为一致性在自己维护的部分延续同一许可。
- 本次没有改写上游 LICENSE 或移除原作者头。native/link.c 与 test/sio-rom.cjs 另加 SPDX 标识并保留移植出处。
- 第三方商标、游戏名称、ROM、汉化/修改版内容和用户存档不在源码许可授权范围内；不能声称上游或游戏权利人为此项目背书。

## 2. 参考代码与真正运行的代码

实际编译的是 vendor/mgba 中 tangobattle/mgba fork 的 GBA 最小核心和 SIO driver。mGBA 上游为 mgba-emu/mgba，固定 fork 版本与原始许可在来源表中列明。

mgba-rollback 的协作调度和测试ROM、mgba-rs 的 SIO 用户胶水经过 C/JavaScript 适配；不是把整个 Rust 工程编译成网页。reference 保留原始算法资料，不代表其中的 getgud、tango 或 Cargo 依赖已经进入本项目。当前没有预测回滚，文档和产品不得因引用了 rollback 仓库就宣称实现 rollback。

公开Tango仓库附有GPLv3文本；参考副本中的throttler又说明来源为非公开tango-pvp，二者不能混同。该Rust实现当前未编译，更上游许可链未独立核验。未来引入回滚、节流或其依赖时应另行检查，而不是由项目根MPL推断许可。

本次构建清单含 inih 配置解析对象。随 vendor 存放的 libpng、zlib、SQLite、LZMA、Discord 等没有在当前对象/链接清单中出现为已启用第三方库；但分发这些源码本身仍要保留它们各自许可。尤其 contrib 示例、嵌套库不能只看所在目录主许可证。

## 3. 分发源码或 JS/WASM 时要做什么

按 [MPL §3.1–3.4](<https://www.mozilla.org/en-US/MPL/2.0/>)：保留覆盖代码的版权、许可、免责声明等实质声明；向接收者说明适用 MPL 及取得文本的方式。分发可执行形式时，还需让接收者能以合理方式及时取得对应的受 MPL 覆盖源码，且不能用可执行文件的条款剥夺相应源码权利。

[Mozilla 官方 FAQ](<https://www.mozilla.org/en-US/MPL/2.0/FAQ/>) 对网络场景作了区分：仅运行在服务器而未交付副本的代码，与发送给浏览器的代码不同。本项目会发送 JS/WASM，所以不能仅以“这是网页服务”或“GitHub 是私有”跳过客户端覆盖代码的源码可得性安排。

部署者应在开放服务前选择实际可用的方案：

1. 给所有相应接收者授予能获取匹配版本源码的仓库访问权限；或
2. 单独提供不含 ROM、口令、存档的对应源码包，并在界面/分发材料说明取得位置与版本。

私有仓库并非必须改成公开，但**只有管理员能访问的私库 URL 不是所有浏览器接收者已经能取得源码的证据**。当前页面有“开源许可与来源”入口，附带许可原文；该入口不自动实现源码包下载。当前部署模板也不会把整个项目根目录公开为文件服务器，源码交付必须由部署者另行安排。

对应源码至少应覆盖实际使用的 mGBA/适配修改、构建配置和相关构建脚本，而不是只给上游 main 分支链接。保留当前源码树、固定 commit、工具链版本和实际 JS/WASM 标识，避免提供与下载二进制不对应的源码。若提供整个源码包，仍排除用户 ROM、密钥、存档和本机缓存，保留上游文件原许可。

## 4. 生成物和镜像中的独立许可

生成 JS 胶水包含 Emscripten 代码；WASM 使用 C/数学/分配器等运行库。它们的 MIT、NCSA、musl 文件级声明、Apache-2.0 WITH LLVM-exception 或 public-domain/CC0 声明不能被根 MPL 代替。

仓库 [licenses](<../licenses/>) 保存已核对的原文副本，[NOTICE](<../NOTICE>) 提供摘要。浏览器 [许可页面](<../public/legal/notices.html>) 随静态站点分发相关声明；Docker 镜像同时保留 NOTICE、licenses 和本文。它们是归属材料，不是已完成逐符号 SBOM 或所有素材法律审计的保证。

若改 SDK、构建开关、启用压缩/图片/数据库/Discord 库，或新增 npm 依赖，需要重新检查并更新许可清单。inih 的 BSD 条款、MIT 的版权许可文本、Apache 的原始 NOTICE 与适用例外应按各自条件保留；不要以“只有开发依赖”替代对实际再分发内容的检查。

Node.js/Caddy 是外部运行时或部署镜像。正式项目不将本机 Node 二进制纳入 Git；若另行分发 Node、Caddy 或完整容器镜像，应保留相应发行版本及其依赖的许可材料，而非只复制本项目 LICENSE。工具名和镜像标签也不代表商标授权。

私有仓库、加密传输、署名、访问口令或“仅供测试”文字都不自动授予复制、托管、公开下载、商用或再分发权利。转公开、发发行包或对外提供 ROM 前，应独立确认权利；必要时从对应分发物中移除 ROM，仅保留源码与配置模板。移除当前文件不等于清除 Git 历史中的旧副本，若需要对外生成无 ROM 源码包，应从受控的允许清单导出，不直接打包整个已有私有历史。
